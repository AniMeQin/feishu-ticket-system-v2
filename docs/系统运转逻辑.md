# V2 工单系统运转逻辑

本文说明生产版 `1.1.10-lite` 的业务规则、状态变化、权限边界、写入确认和补偿机制。字段及部署参数见[字段与部署](字段与部署.md)，故障处置见[运维与故障排查](运维与故障排查.md)。

## 1. 核心原则

1. **多维表格是唯一真实状态源。** 群卡片和私聊卡片都必须从表格当前记录生成。
2. **流程版本控制旧卡片。** 每次业务变更递增“流程版本”；旧卡片点击后只刷新，不再执行写入。
3. **成功必须有落库依据。** 写入响应明确成功，或回读记录与目标更新一致，才返回成功卡片。
4. **通信期限不是业务期限。** 飞书要求卡片回调约三秒内完成；`2850ms` 只用于控制通信，不用于判断工单最终是否成功。
5. **关键写入同步完成。** 不把多维表格关键更新放到响应结束后的后台 Promise，也不依赖腾讯云异步执行。
6. **跨卡片操作最终一致。** 当前卡片即时返回，其他群卡片和报修人卡片由 `/jobs/sync` 根据表格真实状态修复。
7. **最小表结构。** 不新增审批表、任务表、独立状态表或延期字段；可观测性优先使用云函数结构化日志。

## 2. 组件职责

| 组件 | 职责 | 不承担的职责 |
| --- | --- | --- |
| 飞书原生表单 | 收集报修信息并生成记录 | 不计算状态、SLA 或权限 |
| 多维表格工单主表 | 保存全部业务状态和卡片 ID | 不主动保证卡片一致性 |
| 主 Web 函数 | 回调鉴权、状态校验、字段写入、卡片生成、同步和 SLA 检查 | 不修改表结构 |
| IT 群卡片 | 接单、拒绝、更新、延期和提交结果 | 不作为真实状态源 |
| 报修人私聊卡片 | 确认恢复或反馈未恢复 | 不允许非报修人操作 |
| `/jobs/sync` | 按记录定向同步，或在无记录 ID 时执行全量初始化、补卡和刷新 | 不改变业务状态 |
| SLA 调度器 | 每 5 分钟调用 `/jobs/sla` | 不持有飞书 App Secret，不直接读写表格 |

## 3. 新工单初始化

### 3.1 触发来源

- 首选：飞书记录新增事件把记录 ID 发送到 `/feishu/events`。
- 补偿：`/jobs/sync` 扫描到没有工单号或缺少报修人 OpenID 的记录时执行初始化。

### 3.2 初始化步骤

1. 读取新记录。
2. 每隔 `BITABLE_RECORD_SETTLE_INTERVAL_MS` 重新读取一次，最多三次，等待表单字段稳定。
3. 识别系统“提交人”；无法识别时停止创建。
4. 校验“报修人”与实际提交人一致；不一致时以 `REPORTER_MISMATCH` 拒绝，完全禁止代报修。
5. 获取报修人 OpenID；可用时补充人员字段和联系电话。
6. 生成工单号：`IT-YYYYMMDD-记录ID后六位`。
7. 写入初始状态“待处理”、流程版本、报修时间、优先级、SLA 截止时间、是否曾经超时和返工次数。
8. 向 IT 群发送待处理卡片，将消息 ID 写回“当前群卡片 ID”。

发送新卡片使用稳定 UUID。同一记录重复初始化不会重复创建同一张消息。

## 4. 卡片回调处理链路

### 4.1 请求入口

1. 限制请求体不超过 `256KB`。
2. 使用 Encrypt Key 解密加密事件。
3. 校验 Verification Token；失败返回 `401`。
4. 校验飞书签名和五分钟时间窗。因腾讯云代理可能改变原始请求体，签名不一致会记录告警；只有解密和 Token 校验失败才拒绝合法回调。
5. 使用飞书 `event_id` 做当前实例内去重；最多保留 1000 个事件状态。
6. 日期选择器等非按钮回调直接返回空响应，不推进业务流程。

### 4.2 单次业务操作

1. 为同一 `record_id` 建立当前实例内操作锁，防止重复点击并行执行。
2. 读取表格当前记录。
3. 校验卡片流程版本、当前状态、操作人权限和输入。
4. 计算目标字段及新版本号。
5. 发起一次多维表格写入。
6. 写入返回的记录完整匹配目标字段时立即确认成功。
7. 写入响应不明确时，在剩余通信窗口内回读记录；目标状态已经落库则按成功处理。
8. 仍无法确认时返回“暂未确认工单已更新”，释放事件去重状态，允许用户在确认表格没有变化后重试。
9. 确认成功后记录结构化业务日志，并直接返回由真实记录生成的新卡片。

### 4.3 并发边界

- `actionLocks` 和 `event_id` 去重都只在单个 Node.js 进程内有效。
- 生产 SCF 必须保持最大并发 `1`，避免两个实例同时读取同一版本后覆盖写入。
- 如果未来需要提高并发，必须先实现跨实例条件更新、分布式锁或其他 CAS 机制；仅调大云函数并发是不安全的。

## 5. 操作规则矩阵

| 操作 | 允许状态 | 操作人 | 必填 | 成功后的关键变化 |
| --- | --- | --- | --- | --- |
| 接单 | 待处理 | IT 白名单或管理员 | 无；预计完成时间选填 | 处理中；未填时预计完成时间为接单时间加 30 个自然分钟，手动填写时采用所选时间；写入处理人、接单时间、预计完成时间、当前进展、版本 |
| 拒绝并关闭 | 待处理 | IT 白名单或管理员 | 拒绝原因 | 已关闭；写入处理结果、拒绝进展、关闭时间、版本 |
| 更新进展 | 处理中 | 当前处理人或管理员 | 当前进展 | 更新当前进展和版本，状态不变 |
| 延期 | 处理中 | 当前处理人或管理员 | 新预计完成时间 | 新时间必须更晚；只更新预计完成时间和版本 |
| 提交处理结果 | 处理中 | 当前处理人或管理员 | 处理结果 | 待用户确认；写入处理结果和版本，同时结算是否曾经超时 |
| 故障已恢复 | 待用户确认 | 原报修人 | 无 | 已关闭；写入关闭时间和版本 |
| 故障未恢复 | 待用户确认 | 原报修人 | 无 | 处理中；返工次数加一，清空处理结果和用户卡片 ID，更新版本 |

管理员可以代替当前处理人执行 IT 侧操作，但不能代替报修人确认恢复。

## 6. 旧卡片和输入控件

### 6.1 旧卡片

卡片提交的版本与表格当前“流程版本”不一致时：

- 不执行任何业务写入；
- 读取并返回表格当前状态对应的卡片；
- 提示“已刷新为工单的最新状态”；
- 日志记录 `stale_card_refreshed`。

### 6.2 日期时间选择器

飞书选择日期时间时会单独发送 `picker_datetime` 回调。系统只保存用户在卡片表单中的编辑状态，不把选择控件误判成“接单”或“延期”。只有 `tag=button` 的明确按钮提交才执行操作。

时间输入支持 Unix 秒、Unix 毫秒、ISO 时间、`YYYY-MM-DD HH:mm` 以及中文年月日时分格式；无时区文本按上海时间解释。

## 7. 卡片同步与补偿

`/jobs/sync` 支持两种模式，均只修复显示和通知，不改变工单业务状态：

- **定向模式**：请求携带 `record_id` 时，只读取和同步当前工单；用于“流程版本变化”即时自动化。
- **全量模式**：未携带 `record_id` 时扫描全部工单；用于每日三次兜底和人工补偿。

无论哪种模式，待用户确认且缺少私聊卡片的记录都会优先发送用户确认卡片，再刷新群卡片或历史关闭卡片。即使即时自动化暂时仍未传记录 ID，也不会再让历史卡片刷新阻塞当前用户通知。

### 7.1 活动工单

- 缺少工单号或报修人 OpenID：执行初始化或身份修复。
- 待处理、处理中、待用户确认且缺群卡片：补发群卡片并写回消息 ID。
- 待用户确认且缺报修人卡片：优先发送私聊确认卡片并写回消息 ID。
- 已有群卡片：随后按表格当前记录刷新。

### 7.2 已关闭工单

- 关闭后 24 小时内刷新已有群卡片和报修人卡片为关闭状态。
- IT 拒绝关闭且尚未通知报修人时，补发拒绝通知。
- 超过 24 小时后停止重复 PATCH，控制扫描耗时。

### 7.3 触发策略

- 多维表格“流程版本变化”自动化立即调用一次 `/jobs/sync`，请求体传入当前触发记录的 `record_id`。
- 每天 `09:00、13:30、17:30` 各调用一次不带 `record_id` 的全量兜底扫描。
- 自动化只监听“流程版本”，不要监听卡片 ID，避免写回消息 ID 后循环触发。

## 8. SLA 计算

### 8.1 工作时间

- 周一至周五：`08:00-12:00`、`13:00-17:00`。
- 午休 `12:00-13:00` 不计时。
- 周六、周日永远不计时，即使是国家调休工作日。
- 法定节假日不计时；代码内置 2026 年日期，其他年度通过 `SLA_HOLIDAYS` 追加。
- 所有计算使用 `Asia/Shanghai`。

### 8.2 优先级

默认值为 P3，可通过环境变量调整：

| 优先级 | 默认 SLA |
| --- | --- |
| P1（紧急） | 1 个工作小时 |
| P2（高优） | 2 个工作小时 |
| P3（普通） | 8 个工作小时 |
| P4（低优） | 40 个工作小时 |

### 8.3 超时处理

1. 初始化时根据报修时间、优先级和工作日历生成“SLA 截止时间”。
2. IT 提交处理结果时立即结算是否超过 SLA；报修人等待确认时间不计入 SLA。
3. 独立调度函数每 5 分钟调用 `/jobs/sla`，检查仍在待处理或处理中的记录。
4. 首次超时时写入“是否曾经超时=是”并向群发送一次提醒。
5. 提醒成功后写入“SLA 首次提醒时间”，避免重复提醒。
6. “是否曾经超时”一旦为“是”永不恢复。

## 9. 一致性与错误语义

| 情况 | 用户看到的结果 | 系统后续动作 |
| --- | --- | --- |
| 写入并确认成功 | 成功提示和新卡片 | 定向 `/jobs/sync` 优先通知当前报修人并更新当前卡片 |
| 写入响应慢，但回读已落库 | 成功提示和新卡片 | 正常同步 |
| 通信窗口内无法确认 | “暂未确认，请以最新卡片和多维表格为准” | 状态变化自动化或兜底同步修复卡片 |
| 旧卡片 | 最新状态卡片 | 不写表 |
| 权限、状态或输入错误 | 明确错误提示 | 不写表 |
| 解密或 Token 错误 | HTTP 401 | 不进入业务逻辑 |
| 同步中某条失败 | 任务继续扫描其他记录并累计 `failed` | 日志保留 record ID 和错误原因 |

系统提供“最终一致”而不是跨飞书 API、表格和消息系统的分布式事务。任何判断都以表格当前记录为准。

## 10. 状态机

```text
表单提交
  -> 待处理
      -> 接单 -> 处理中
          -> 更新进展 -> 处理中
          -> 延期 -> 处理中
          -> 提交处理结果 -> 待用户确认
              -> 用户确认恢复 -> 已关闭
              -> 用户反馈未恢复 -> 处理中
      -> 拒绝并关闭 -> 已关闭
```

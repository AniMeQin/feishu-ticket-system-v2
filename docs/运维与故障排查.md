# 运维与故障排查

本文用于生产巡检和故障处置。排查顺序固定为：**多维表格真实状态 → 主函数最新日志 → 群/私聊卡片 → 自动化与调度器**。不要先反复点击卡片或直接修改表结构。

## 1. 正常运行基线

| 检查项 | 正常信号 |
| --- | --- |
| 主函数 | 腾讯云状态正常，就绪检查 `/health` 通过 |
| `/health` | `version=1.1.10-lite`、`ready=true`、`missing=[]` |
| 卡片回调 | 日志出现 `card_action received`，之后出现 `record_updated`、`readback_confirmed` 或 `stale_card_refreshed` |
| 同步任务 | `scheduled_job completed`，`job=sync`，`failed=0` |
| SLA 任务 | 每 5 分钟出现 `scheduled_job completed`，`job=sla` |
| 群卡片 | 状态和多维表格一致 |
| 用户卡片 | 待用户确认时出现；关闭后与群卡片一致 |
| 云函数并发 | 最大并发保持 `1` |

## 2. 结构化日志

### 2.1 卡片操作阶段

| `phase` | 含义 |
| --- | --- |
| `received` | 已收到明确的业务按钮操作 |
| `input_ignored` | 日期选择器等非按钮回调已忽略，属于正常行为 |
| `record_loaded` | 已读取当前状态和流程版本 |
| `write_unconfirmed` | 写入响应暂时不明确，随后应检查回读或同步结果 |
| `readback_started` | 正在回读多维表格确认实际落库 |
| `record_updated` | 写入响应已确认目标字段 |
| `readback_confirmed` | 写入响应不明确，但回读确认已落库 |
| `stale_card_refreshed` | 用户点击旧卡片，未写表，已返回最新卡片 |
| `card_ready` | 新卡片已经生成 |
| `response_sent` | 已向飞书返回卡片响应 |
| `failed` | 操作未完成；结合 `code`、`message` 和 `durationMs` 判断 |

飞书约三秒的卡片通信窗口可能使日志出现内部 `ACTION_TIMEOUT`，但业务判断必须继续查看多维表格和紧随其后的 `/jobs/sync`。如果表格已更新，说明业务已经落库，不能把通信提示当成业务失败。

### 2.2 同步任务结果

`/jobs/sync` 的结果字段：

| 字段 | 含义 |
| --- | --- |
| `mode` | `targeted` 表示定向当前工单；`full` 表示全量补偿 |
| `recordId` | 定向同步的记录 ID；全量模式为空 |
| `scanned` | 本次扫描记录数 |
| `initialized` | 新初始化工单数 |
| `repaired` | 补全身份、补发卡片或通知数 |
| `refreshed` | 刷新卡片总数 |
| `refreshedClosed` | 刷新的最近关闭群卡片数 |
| `refreshedReporterClosed` | 刷新的最近关闭报修人卡片数 |
| `skippedClosed` | 超过补偿窗口或无可刷新卡片的关闭工单数 |
| `failed` | 失败记录数；生产正常值为 0 |
| `errors` | 失败的 record ID 和错误原因 |

### 2.3 SLA 任务结果

| 字段 | 含义 |
| --- | --- |
| `scanned` | 扫描记录数 |
| `breached` | 本次首次标记超时数 |
| `alerted` | 本次首次提醒成功数 |
| `failed` | 失败记录数 |

## 3. 常见故障

### 3.1 卡片提示 `200671`

常见原因：回调加密配置和函数环境变量不一致。

检查顺序：

1. 飞书开放平台 Encrypt Key 与 `FEISHU_ENCRYPT_KEY` 是否完全一致。
2. Verification Token 与 `FEISHU_VERIFICATION_TOKEN` 是否完全一致。
3. 是否部署了旧代码包。
4. 日志是否出现 `decrypt failed` 或 `invalid verification token`。
5. 修改环境变量后是否重新部署并等待实例更新。

不要关闭 Token 校验。正确做法是让飞书控制台和腾讯云环境变量保持一致。

### 3.2 点击后提示“暂未确认”

这表示在飞书通信窗口内尚未取得确定结果，不等于业务失败。

1. 先查看多维表格记录和流程版本。
2. 表格已变化：等待状态变化自动化或执行一次 `/jobs/sync`，不要重复点击旧卡片。
3. 表格未变化：使用最新卡片重试一次。
4. 日志若只有 `received`、没有 `record_loaded`，检查飞书 API 读取延迟和 App 凭证。
5. 日志出现 `write_unconfirmed` 后，应继续查随后几秒内的表格状态和同步日志。

### 3.3 提示成功但表格未变化

`1.1.10` 不应出现此现象。若出现：

1. 核对 `/health` 版本是否为 `1.1.10-lite`。
2. 检查是否仍有旧函数 URL、旧飞书回调或旧卡片指向旧环境。
3. 查找同一 `recordId` 的 `record_updated` 或 `readback_confirmed`；不存在时保留日志并停止重复操作。
4. 重新部署当前已验收压缩包，不要恢复最初旧版。

### 3.4 旧卡片没有推进流程

这是正常保护。旧卡片应显示“已刷新为工单的最新状态”，日志为 `stale_card_refreshed`。在刷新后的当前卡片继续操作。

### 3.5 选择日期时间后没有变化

这是正常行为。选择器只编辑表单，必须再点击“接单”或“延期”按钮。日志中的 `input_ignored` 不是错误。

### 3.6 多维表格已变化，但群卡片未更新

1. 检查“当前群卡片 ID”是否存在。
2. 检查“流程版本变化”自动化是否调用 `/jobs/sync`。
3. 检查 Authorization 是否使用 `FEISHU_INTERNAL_JOB_TOKEN`。
4. 查看同步结果中的 `failed` 和 `errors`。
5. 确认飞书应用仍在 IT 群中，且具备更新自己发送消息的权限。

### 3.7 待用户确认，但没有私聊卡片

1. 核对“报修人 OpenID”是否存在且属于真实提交人。
2. 检查“流程版本变化即时同步”的请求体是否传入当前触发记录的 `record_id`。
3. 检查同步结果是否为 `mode=targeted`、`scanned=1`、`failed=0`；若仍是 `mode=full`，说明代码已兼容运行，但飞书自动化尚未完成定向配置。
4. 检查“当前用户卡片 ID”是否写回，并查看 `repair_reporter_confirmation` 的重试和错误日志。
5. 确认用户可以接收该飞书应用消息，且应用权限已发布生效。
6. 必要时执行一次带当前 `record_id` 的 `/jobs/sync`，不要先重复点击“提交处理结果”。

### 3.8 用户确认后表格关闭，但群卡片未关闭

先确认表格状态“已关闭”和关闭时间已经写入。随后检查流程版本自动化及 `/jobs/sync` 的 `refreshedClosed`、`refreshedReporterClosed`。关闭后 24 小时内系统会继续补偿；超过窗口后不再反复 PATCH。

### 3.9 SLA 没有运行

1. 腾讯云调度器监控中每 5 分钟应增加一次调用。
2. 调度器环境变量 `TARGET_URL` 必须指向当前主函数。
3. `INTERNAL_JOB_TOKEN` 必须与主函数 `FEISHU_INTERNAL_JOB_TOKEN` 一致。
4. 主函数日志应出现 `scheduled_job received` 和 `scheduled_job completed`，`job=sla`。
5. 如果调度器报 HTTP 401，优先检查 Token；如果超时，检查主函数公网访问和执行状态。

### 3.10 `/health` 显示 `ready=false`

查看 `missing` 数组并补齐对应环境变量。配置完成后重新部署或重启实例。`FEISHU_ADMIN_OPEN_IDS`、`FEISHU_EVENT_TABLE_ID` 和 `FEISHU_BITABLE_URL` 为空不会导致未就绪。

## 4. 应急处置

### 4.1 单张工单异常

1. 记录工单号、record ID、操作时间和操作人。
2. 截止现场重复点击；先保存群卡片和错误提示截图。
3. 在多维表格确认当前状态和流程版本。
4. 按 `recordId` 和时间范围过滤主函数日志。
5. 如果表格正确、卡片错误，执行 `/jobs/sync`；不要手工修改卡片 ID。
6. 如果表格未写入，使用最新卡片重试一次。
7. 仍失败时保留日志，修复代码后走完整发布流程。

### 4.2 多张卡片不同步

1. 暂停造成重复调用的错误自动化，但不要停主函数。
2. 修正自动化 Header、URL 或应用权限。
3. 手动执行一次 `/jobs/sync`。
4. 确认结果 `failed=0`；若不为 0，按 `errors` 逐条处理。
5. 恢复流程版本变化自动化和每日兜底任务。

### 4.3 主函数不可用

1. 检查最新部署日志、函数状态和就绪检查。
2. 确认压缩包根目录和 `scf_bootstrap` 权限正确。
3. 检查必填环境变量；不要在日志或工单群粘贴真实 Secret。
4. 重新部署最近一次已经完成真实验收的 V2 构建物。
5. 服务恢复后执行 `/jobs/sync`，补偿停机期间记录和卡片。

## 5. 定期维护

| 周期 | 工作 |
| --- | --- |
| 每日 | 查看主函数失败率、同步 `failed`、SLA 调度器调用次数 |
| 每周 | 抽查一张活动工单的表格、群卡片和私聊卡片一致性 |
| 人员变更时 | 更新 `FEISHU_IT_OPEN_IDS` 和 `FEISHU_ADMIN_OPEN_IDS`，重新部署并测试权限 |
| Secret 轮换时 | 同步更新飞书平台、主函数和调度器相关变量，重新执行 URL 验证和真实卡片测试 |
| 每年放假安排发布后 | 更新 `SLA_HOLIDAYS` 或代码内置日历，并增加时间计算测试 |
| 每次发布 | 更新版本号、`APP_COMMIT`、文档、测试和真实生产验收记录 |

云日志建议保留 365 天并由平台到期自动删除。日志中记录工单号、record ID、状态和 OpenID，但不得记录 App Secret、Encrypt Key、Verification Token 或内部任务 Token。

## 6. 已知技术边界

- 飞书卡片回调约三秒，无法保证所有网络条件下都在一次响应内确认写入。
- 多维表格、消息系统和云函数之间没有分布式事务，依靠表格真实状态和 `/jobs/sync` 达到最终一致。
- 事件去重和同记录操作锁是进程内机制，因此生产并发必须保持 `1`。
- `/jobs/sync` 和 `/jobs/sla` 当前扫描全部记录；数据量显著增长后应评估分页增量策略和 15 秒执行上限。
- 已关闭卡片只补偿 24 小时，超出窗口后不再自动刷新历史消息。
- 2026 年节假日内置；后续年度必须主动维护。
